# 키트가 배운 점

키트를 만들고 고치면서 배운 것을 적는다. 프로젝트에서 올라온 것 중 어느 프로젝트에서나 통하는 것도 여기에 모인다.

항목 형식(새 항목은 맨 아래 "여기부터 항목" 표시 바로 밑에 넣어, 최근 것이 위로 오게 한다):

```
## YYYY-MM-DD 한 줄 제목
- 상황: 무슨 일을 하다가 생겼는지
- 근거: 사용자의 말이나 명령 출력 그대로
- 원인: 왜 생겼는지
- 고칠 자리: 훅·권한 / 스킬 / 서브에이전트 / 템플릿 / 고칠 것 없음
- 상태: 관찰됨
```

상태는 다음 중 하나다: 관찰됨, 제안됨, 적용됨, 되돌림, 폐기.

## 2026-11-16 사용자 컴퓨터의 개인 스킬이 비교 시험에 섞인다
- 상황: 디자인 플러그인을 "쓰기 전/후"로 비교했다.
- 근거: 첫 시험에서 frontend-design 유무의 차이가 없었는데, 개인 스킬 폴더에 impeccable과 design-taste-frontend가 있어 "스킬 없이" 실행도 그것을 부를 수 있는 상태였다. 스킬을 못 박고 다시 실행하니 frontend-design만 뚜렷이 다른 화면을 냈다.
- 원인: 대화 없는 실행도 개인 스킬을 읽는다. 시험 절차에 이를 막는 단계가 없었다.
- 고칠 자리: 스킬 (`scout`의 디자인 시험 절차에 "쓸 스킬을 못 박고 나머지는 막는다"를 더함)
- 상태: 적용됨

## 2026-11-16 스킬 없이 만든 화면과 두 디자인 스킬의 화면이 같은 모습으로 모였다
- 상황: 같은 가계부 소개 페이지를 네 방식으로 만들어 띄워 봤다.
- 근거: 스킬 없이, impeccable, design-taste-frontend 세 결과가 모두 크림색 바탕에 초록, 왼쪽 큰 제목과 오른쪽 휴대폰 미리보기였다. frontend-design만 달랐다.
- 원인: 모델의 기본 취향이 강하고, 만들기 용도로 부른 두 스킬이 그 취향을 바꾸지 못했다(design-taste-frontend는 핵심인 브라우저 검사가 돌지 못한 조건이었다).
- 고칠 자리: 고칠 것 없음 (채택 판단에 반영: impeccable은 만들기가 아니라 점검·다듬기 역할로 채택)
- 상태: 관찰됨

## 2026-11-16 훅 본이 ES 모듈 방식 프로젝트에서 실패했다
- 상황: 사용자가 실제 프로젝트에서 `/vibe-kit:setup`을 처음 실행했다.
- 근거: 그 실행의 보고: "처음 훅을 실행하자 `ReferenceError: require is not defined in ES module scope`로 실패했습니다. 훅 파일은 CommonJS인데 이 프로젝트의 `package.json`이 `"type": "module"`이라서입니다."
- 원인: 훅 본의 확장자가 `.js`라서 프로젝트의 모듈 설정을 따라갔다. 키트의 시험 프로젝트에는 그런 설정이 없었다.
- 고칠 자리: 템플릿 (`templates/hooks/`의 훅 본을 `.cjs`로 바꾸고, 검증 스크립트가 ES 모듈 방식 폴더 안에서 훅을 실행해 본다)
- 상태: 적용됨 (변경 제안 fix/setup-esm-and-paths)

## 2026-11-16 스킬 글 안의 프로젝트 경로 변수는 읽을 때 실제 경로로 바뀐다
- 상황: 같은 실행에서 훅 등록 예시를 `settings.json`에 옮겼다.
- 근거: 그 실행의 보고: "스킬 안내의 훅 등록 예시는 `S:/Workspace/.claude/hooks/`를 가리켜서 이 프로젝트 경로로 고쳐 썼습니다." 공식 문서(skills, "Available string substitutions")도 스킬 글 안의 프로젝트 경로 변수를 바꿔 넣는다고 적는다.
- 원인: 설정에 그대로 옮겨야 할 변수를 스킬 글의 코드 블록에 적었다. 또 그 세션은 프로젝트의 위쪽 폴더에서 열려 있어, 바뀐 경로가 프로젝트가 아닌 위쪽 폴더였다.
- 고칠 자리: 스킬 (등록 예시를 본 파일 `templates/hooks/settings-hooks.json`으로 옮기고, 세션이 프로젝트 폴더에서 열렸는지 먼저 확인하게 했다. 검증 스크립트가 스킬 글에 그 변수가 있으면 실패한다)
- 상태: 적용됨 (변경 제안 fix/setup-esm-and-paths)

## 2026-11-16 setup이 본의 묻기 규칙을 뺐고, 규칙 경로가 빌드 결과물 폴더를 가리켰다
- 상황: 같은 실행의 결과.
- 근거: 그 실행의 보고: "템플릿의 `ask`에 있던 `git push *`는 뺐습니다", "적용 경로는 `dist/**`와 `*.test.mjs`입니다"(같은 프로젝트에 `npm run build:standalone` 명령이 있음).
- 원인: 스킬 글에 본의 묻기·막기 규칙을 느슨하게 할 조건과, 규칙 경로가 원본 파일을 가리켜야 한다는 말이 없었다. 묻기 규칙은 사용자가 그 세션에서 허용한 것으로 보이고, `dist`가 원본인 프로젝트일 수도 있어 잘못이라고 단정할 수는 없다.
- 고칠 자리: 스킬 (묻기·막기 규칙은 사용자가 분명히 요청했을 때만 바꾸고 결과를 적는다. 규칙 경로는 원본 파일을 가리키고, 결과물 폴더를 가리킬 때는 근거를 적는다)
- 상태: 적용됨 (변경 제안 fix/setup-esm-and-paths)

## 2026-11-16 세션 시작 훅의 "환경 없음" 안내가 무관한 작업의 답에 붙는다
- 상황: 키트 환경이 없는 임시 폴더에서 다른 과제(서버 코드 쓰기, 자동화 추천)를 대화 없이 실행했다.
- 근거: 두 실행의 답 끝에 각각 "이 폴더에는 vibe-kit 환경이 아직 없습니다. 필요하면 `/vibe-kit:setup`을 실행하세요.", "vibe-kit 환경이 필요하면 `/vibe-kit:setup` 한 줄로 만들 수 있습니다"가 붙었다. (같은 날 2회)
- 원인: 훅이 환경 없는 모든 폴더에서 안내를 넣고, 거절을 기억할 방법이 없다. 스크립트나 일회성 폴더에서도 매번 붙는다.
- 고칠 자리: 훅·권한 (`hooks/session-start.js`: 뿌리에 .git이 있는 폴더에서만, 새 세션에서만, 폴더마다 한 번만 안내한다. 요청한 일을 먼저 하고 코드 작업일 때만 끝에 한 줄로 알리게 문구를 바꿨다)
- 상태: 적용됨 (변경 제안 fix/session-start-quiet)
