# improve: 돌아가는 프로젝트를 낫게 한다

사용자는 무엇이 문제인지 스스로 짚지 못할 수 있다. 그래서 에이전트가 먼저 살펴보고, 사용자는 **고르기만** 하면 되게 한다.

세 가지를 지킨다.

- **돌아가던 것을 망가뜨리지 않는다.** 살펴보는 동안에는 아무것도 바꾸지 않는다. 고칠 때는 하나씩 고치고 매번 확인한다.
- **고르는 것은 사용자다.** 찾은 것을 스스로 고치기 시작하지 않는다.
- **쉬운 말로 말한다.** "무엇이 문제인가"를 코드가 아니라 쓰는 사람에게 생기는 일로 설명한다.

순서: 파악 → 살펴보기 → 목록 보여 주기 → 고르기 → 하나씩 고치기 → 기록.

## 1단계: 파악한다 (읽기만)

1. 세션이 프로젝트 폴더에서 열렸는지 본다. 상위 폴더에서 열렸으면 프로젝트 폴더에서 다시 열자고 안내하고 멈춘다.
2. 프로젝트의 형태, 언어, 실행·빌드·테스트 명령, 쓰는 사람을 알아낸다. `AGENTS.md`와 `docs/agent/`가 있으면 그것을 먼저 읽는다. 없어도 계속한다(키트 환경이 없으면 3단계 목록에 "키트 환경 만들기"를 한 항목으로 넣는다).
3. git 상태를 본다. 커밋하지 않은 수정이 있으면 그 사실을 적어 둔다(5단계에서 쓴다). git 저장소가 아니면 그 사실을 적어 둔다.
4. 사용자가 인자나 말로 걱정되는 곳을 알려 주었으면 그곳을 먼저, 더 깊게 본다. 그 말이 모호하면 `clarify` 스킬의 방법으로 뜻을 알아낸다.

## 2단계: 살펴본다 (읽기만)

아래 분야 가운데 **이 프로젝트에 해당하는 것만** 본다. 해당하지 않는 분야는 건너뛰고 건너뛴 이유를 적는다. 읽는 양이 많으면 `vibe-kit:researcher` 서브에이전트에 분야별로 맡긴다.

실제로 실행해 본 것과 코드만 읽고 짐작한 것을 구분해 적는다. 실행하지 못한 확인을 통과로 적지 않는다.

| 분야 | 보는 것 | 확인 방법 |
|---|---|---|
| 돌아가는가 | 빌드·실행이 되는가, 테스트가 통과하는가, 시작할 때 경고나 오류가 나오는가 | 명령을 실제로 실행한다 |
| 쓰는 사람의 흐름 | 가장 흔한 일을 처음부터 끝까지 해 본다. 막히는 곳, 안내가 없는 곳, 빈 화면·오류·기다림 상태 | 화면이 있으면 띄워서 눌러 본다. 명령줄 도구면 도움말과 잘못된 입력을 넣어 본다. 라이브러리면 README의 예제를 따라 해 본다 |
| 보이는 모양 (화면이 있을 때) | 정렬, 여백, 글자 크기의 질서, 색 대비, 작은 화면에서의 모양, 서로 다른 화면 사이의 일관성 | 화면을 띄워 본다. 깔려 있는 디자인 점검 도구가 있으면 쓴다 |
| 접근성 (화면이 있을 때) | 키보드만으로 쓸 수 있는가, 그림과 버튼에 이름이 있는가, 글자 대비 | 띄워서 확인하거나 코드에서 찾는다 |
| 안전 | 저장소에 들어간 비밀값, 사용자 입력을 그대로 쓰는 곳, 누구나 볼 수 있게 열린 것 | 코드와 설정을 읽는다. 비밀 파일의 내용은 읽지 않고 있는지만 본다 |
| 낡은 것 | 지원이 끝난 의존성, 알려진 보안 경고, 큰 버전이 뒤처진 것 | 그 생태계의 "낡은 것 보기" 명령을 실행한다(읽기 전용). 고치는 일은 `freshness`의 절차를 따른다 |
| 확인 수단 | 고친 뒤 망가졌는지 알 방법이 있는가(테스트, 타입 검사, 린트). 가장 중요한 흐름에 테스트가 있는가 | 명령과 테스트 파일을 본다 |
| 고치기 쉬운가 | 같은 코드의 반복, 지나치게 큰 파일, 쓰이지 않는 코드, 오류를 삼키는 곳 | 코드를 읽는다 |
| 빠른가 | 눈에 띄게 느린 곳, 지나치게 큰 내려받기, 같은 일을 되풀이하는 곳 | 실행해서 잰다. 재지 못했으면 짐작이라고 적는다 |
| 설명과 환경 | 새 사람이 README만 보고 실행할 수 있는가, 에이전트 지시 파일이 지금 코드와 맞는가 | 적힌 명령을 실행해 본다 |

## 3단계: 목록을 보여 준다

찾은 것을 **다섯 개에서 열 개 사이**로 추린다. 더 많이 찾았으면 효과가 큰 것만 남기고 "그 밖에 n개"로 묶어 따로 적는다. 사소한 것으로 목록을 채우지 않는다. 찾은 것이 적으면 적은 대로 보여 준다.

순서는 **쓰는 사람에게 미치는 효과가 크고, 고치기 쉽고, 망가뜨릴 위험이 낮은 것**부터다. 다만 지금 고장 나 있는 것과 안전 문제는 맨 위에 둔다.

각 항목은 아래 꼴로 적는다. 전문 용어는 처음 나올 때 풀어 준다.

```text
1. <한 줄 제목: 쓰는 사람에게 생기는 일로>
   - 지금: <무엇이 어떻게 되어 있는가. 어디서 봤는지(파일, 화면)와 실제로 확인했는지>
   - 고치면: <무엇이 나아지는가>
   - 드는 품: 작음 / 보통 / 큼
   - 위험: 낮음 / 보통 / 높음 (<무엇이 바뀔 수 있는지>)
```

목록 끝에 세 가지를 덧붙인다.

- **먼저 권하는 것**: 두세 개와 그 이유 한 줄.
- **살펴보지 못한 것**: 건너뛴 분야와 실행하지 못한 확인.
- **잘 되어 있는 것**: 두세 줄. 고칠 것만 늘어놓지 않는다.

## 4단계: 고르게 한다

1. 사용자에게 무엇을 할지 묻는다. "번호로 말씀해 주세요. '권하는 것만'이라고 하셔도 됩니다."라고 답하기 쉽게 묻는다.
2. 사용자가 고른 것만 한다. "전부"라고 하면 위험이 높은 항목은 한 번 더 확인받는다.
3. 응답이 없는 것을 동의로 보지 않는다. 사람 없이 도는 실행에서는 3단계 목록을 `docs/agent/STATE.md`의 "다음 할 일"에 적는 데서 멈춘다.

## 5단계: 하나씩 고친다

1. **돌아갈 자리를 만든다.** git 저장소면 시작하기 전의 커밋을 적어 둔다. 커밋하지 않은 사용자 수정이 있으면 그것을 건드리지 않게 주의하고, 먼저 커밋할지 사용자에게 묻는다. git 저장소가 아니면 되돌리기 어렵다는 것을 알리고 진행할지 묻는다.
2. **고치기 전에 확인 수단을 먼저 돌려** 지금 상태를 적어 둔다(통과하던 것이 무엇인지).
3. **한 항목씩** 고친다. 한 항목이 끝나면 확인 수단을 다시 돌리고, 화면이 있는 변경은 화면을 띄워 본다. 통과하던 것이 실패하면 다음 항목으로 넘어가지 않고 원인을 고친다. 두 번 고쳐도 안 되면 그 항목의 변경을 되돌리고 사용자에게 알린다.
4. 항목마다 따로 커밋한다(git 저장소일 때). 하나만 되돌릴 수 있게 하기 위해서다.
5. 고르지 않은 항목은 건드리지 않는다. 고치다가 새로 찾은 것은 목록에 더해 보고한다.
6. 승인이 필요한 일(`AGENTS.md`의 "승인" 절: 의존성 추가와 큰 버전 변경, 파일 삭제, 원격으로 보내기, 배포 등)은 항목을 골랐더라도 그 일을 하기 직전에 다시 승인받는다.

## 6단계: 보고하고 기록한다

1. 보고는 항목마다 세 가지를 적는다: 무엇을 바꿨는가, 무엇으로 확인했는가(실행한 명령과 결과), **사용자가 직접 확인하려면 무엇을 해 보면 되는가**.
2. 되돌리는 방법을 한 줄로 적는다(어느 커밋으로 돌아가면 되는지).
3. `docs/agent/STATE.md`가 있으면 한 일을 "지금까지 한 일"에, 하지 않고 남긴 항목을 "다음 할 일"에 적는다.
4. 고치는 중에 사용자가 바로잡아 준 것은 `docs/agent/LEARNINGS.md`에 적는다.

## 하지 않는 것

- 살펴보는 단계에서 파일을 고치지 않는다. 포매터도 돌리지 않는다.
- 취향 차이일 뿐인 것(이름 짓는 방식, 폴더 배치)을 문제로 올리지 않는다. 쓰는 사람이나 고치는 사람에게 실제로 생기는 일이 있을 때만 올린다.
- 기술 구성을 바꾸자고(다른 프레임워크로 옮기자고) 먼저 제안하지 않는다. 지금 구성으로는 풀 수 없는 문제가 있을 때만, 이유와 함께 맨 끝에 적는다.
- "전체를 새로 짜자"를 제안하지 않는다.

**완료 조건**: 목록을 보여 주었다. 사용자가 고른 항목이 각각 고쳐지고 확인됐거나, 되돌려지고 이유가 보고됐다. 통과하던 확인 수단이 여전히 통과한다. 남은 항목이 기록됐다.
