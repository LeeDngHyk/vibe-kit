# setup: 프로젝트 환경 만들기

이 프로젝트의 형태와 기술에 맞는 환경을 만든다. 특정 기술을 전제하지 않는다. 웹 개발을 기본값으로 가정하지 않는다.

지켜야 할 것:

- 프로젝트의 코드는 사용자의 것이다. 이 스킬은 아래 "만드는 것"에 적힌 파일만 만들고 고친다. 프로젝트 코드는 건드리지 않는다.
- 이미 있는 파일은 덮어쓰지 않는다. 차이를 보여 주고 합친다(4단계).
- 본(템플릿)은 `${CLAUDE_PLUGIN_ROOT}/templates/`에 있다. 본을 그대로 복사하지 않고 이 프로젝트에 맞게 채운다. `{{ }}` 자리표시와 `{{ }}`가 든 줄의 안내는 완성본에 남기지 않는다. `AGENTS.md` 본 첫머리의 주석(`<!-- setup 스킬이 채우는 본이다 ... -->`)도 지운다. `LEARNINGS.md`의 `<!-- 여기부터 항목 -->`은 새 항목을 넣을 자리 표시이므로 남긴다.
- 사용자에게 하는 말은 한국어로, 널리 쓰이는 낱말로 한다. 전문 용어는 처음 나올 때 풀어서 설명한다.

## 1단계: 파악 (읽기만)

다음을 코드와 패키지 파일에서 읽어 알아낸다. 추측한 것은 추측이라고 표시한다.

1. 폴더가 비어 있는지 확인한다. 아무것도 없거나 `.git`, `.gitignore`만 있으면 빈 폴더로 본다. 코드는 없고 README나 메모 같은 글만 있으면 그 글을 읽은 뒤 빈 폴더처럼 3번으로 간다. `AGENTS.md`, `CLAUDE.md`, `.claude/`, `docs/agent/`가 있으면 빈 폴더가 아니다(4단계의 합치기 대상).
2. 비어 있지 않으면 읽는다:
   - 언어와 프레임워크: 패키지·빌드 파일(어떤 생태계의 것이든), 소스 파일의 확장자와 폴더 구조.
   - 빌드·테스트·린트·타입 검사 명령: 패키지 파일의 스크립트, 빌드 도구 설정, 자동화 설정, README.
   - 패키지 관리 도구: 잠금 파일이나 설정으로 알아낸다. 알 수 없으면 추측으로 정하지 않고 2단계 계획에서 사용자에게 묻는다.
   - 결과물의 형태: 화면이 있는가, 누가 어떻게 쓰는가(최종 사용자가 화면으로, 개발자가 명령줄로, 다른 코드가 불러서, 분석 결과를 읽는 사람이 등).
   - 이미 있는 에이전트 설정: `AGENTS.md`, `CLAUDE.md`, `.claude/`, `docs/agent/`.
   - 파일이 많아 탐색이 길어질 것 같으면 `vibe-kit:researcher` 서브에이전트에 맡긴다. 작은 프로젝트는 직접 읽는다.
3. 빈 폴더면 추측하지 않는다. 사용자에게 목표를 묻는다. 아래 한 줄이 질문 하나다. 한 번에 하나만 묻고 답을 받은 뒤 다음으로 간다:
   - 무엇을 만들려는가, 그리고 누가 어떻게 쓰는가(예: 일반 사용자가 휴대폰 화면으로, 개발자가 명령줄에서, 다른 프로그램이 불러서). 이 답에서 결과물 형태를 정한다. 답으로 형태를 알 수 없으면 한 번 더 묻는다.
   - 이미 정한 기술이 있는가. 없으면 목표에 맞는 후보 두세 개를 장단점과 함께 제시한다. 후보는 기억으로 고르지 않고, 공식 문서에서 최신 안정 버전과 유지 상태를 확인한 뒤 제시한다. 웹 조회를 할 수 없으면 후보를 제시하되 "최신 버전과 유지 상태는 확인하지 못했다"고 밝힌다.
   - 사용자가 기술을 아직 고르지 않겠다고 하면 기술 구성과 명령을 "미정"으로 두고 2단계로 간다. 이때는 기술에 기대는 것(규칙 파일, 훅, `settings.json`에 더하는 명령, `STACK.md`의 줄)을 만들지 않고, 기술이 정해진 뒤 `/vibe-kit:setup`을 다시 실행하면 채워진다고 안내한다.

**완료 조건**: 프로젝트 한 줄 설명, 쓰는 사람, 기술 구성(또는 "미정"), 네 가지 명령(없으면 "미정"), 결과물 형태를 각각 한 줄로 말할 수 있다.

## 2단계: 계획 (승인 받기)

아래를 한 화면 분량으로 보여 주고 승인을 받는다. 응답이 없는 것을 동의로 보지 않는다.

1. **파악한 내용**: 1단계 완료 조건의 다섯 항목(한 줄 설명, 쓰는 사람, 기술 구성, 네 가지 명령, 결과물 형태).
2. **만들 파일 목록**: "만드는 것" 절에서 이 프로젝트에 해당하는 것만. 만들지 않는 파일은 이유를 한 줄로 적는다(예: "화면이 없어 visual-design.md는 만들지 않음").
3. **확인 수단**: [verification.md](verification.md)의 표에서 결과물 형태에 맞는 줄을 출발점으로 고르고, 이 프로젝트의 실제 명령으로 바꿔 적는다. 프로젝트에 더 나은 수단이 이미 있으면 그것을 쓴다.
4. **제안할 플러그인**: [adopted-tools.md](adopted-tools.md)에서 이 프로젝트의 형태와 언어에 해당하는 것만. 역할마다 하나만. 각각 이유와 컨텍스트 비용을 적는다. 해당하는 것이 없으면 "제안할 플러그인 없음"이라고 쓴다. 목록에 없는 도구는 제안하지 않는다.
5. **제안할 훅**: 포맷터가 있으면 "수정 후 자동 정리", 타입 검사나 테스트 명령이 있으면 "종료 전 검사". 없으면 제안하지 않는다. 종료 전 검사는 끝낼 때마다 명령이 실행되므로 2분 안에 끝나는 명령만 넣자고 제안한다. 제안하기 전에 그 명령이 이 컴퓨터에서 실제로 실행되는지 확인한다(예: `<도구> --version`). 도구가 설치돼 있지 않으면 훅에 넣지 않고, "도구를 설치한 뒤 `/vibe-kit:setup`을 다시 실행하면 훅을 더할 수 있다"고 계획에 적는다. 설치돼 있지 않은 명령을 종료 전 검사에 넣으면 끝낼 때마다 검사가 실패해 일이 막힌다.

**완료 조건**: 사용자가 계획을 승인했다. 플러그인과 훅은 항목별로 승인 여부가 정해졌다.

## 3단계: 만들기

승인받은 것만 만든다. 해당 없는 파일과 내용이 없는 빈 파일은 만들지 않는다.

### 만드는 것

| 파일 | 본 | 만드는 조건 |
|---|---|---|
| `AGENTS.md` | `templates/AGENTS.md` | 항상 |
| `CLAUDE.md` | `templates/CLAUDE.md` | 항상 |
| `.claude/settings.json` | `templates/settings.json` | 항상 |
| `.claude/rules/user-experience.md` | `templates/rules/user-experience.md` | 사람이 직접 마주하는 부분의 코드 경로가 있을 때 |
| `.claude/rules/visual-design.md` | `templates/rules/visual-design.md` | 화면이 있는 프로젝트만 |
| `.claude/rules/testing.md` | `templates/rules/testing.md` | 테스트 도구가 있고 테스트 파일이 하나 이상 있을 때. 테스트 파일이 아직 없으면 만들지 않는다(이름 관례를 지어내지 않기 위해) |
| `.claude/hooks/` 세 파일 | `templates/hooks/` | 훅을 하나라도 승인받았을 때 |
| `docs/agent/STATE.md`, `STACK.md`, `LEARNINGS.md` | `templates/docs-agent/` | 항상 |

### 파일별 채우는 법

**AGENTS.md** — 60줄을 넘기지 않는다. 더 짧아도 된다. 줄마다 "이 줄을 지우면 실수가 생기는가"를 묻고, 아니면 넣지 않는다. 코드를 읽으면 알 수 있는 내용과 당연한 말은 넣지 않는다. 명령이 없으면 "미정"이라고 쓴다. 도구가 프로젝트에 선언돼 있지만 이 컴퓨터에 설치돼 있지 않으면 명령은 그대로 적고, "확인 수단"에 지금 실행할 수 있는 확인과 설치 뒤에 할 수 있는 확인을 나눠 적는다. "일하는 방식", "끝까지 하기", "알림", "승인" 절은 본의 문장을 그대로 둔다.

**CLAUDE.md** — 본 그대로 둔다. 첫 줄 `@AGENTS.md`는 `AGENTS.md`를 불러오는 줄이다.

**.claude/settings.json** — 본의 권한 규칙에 이 프로젝트의 명령을 더한다.
- `allow`에 더한다: 1단계에서 찾은 테스트·린트·타입 검사·빌드 명령. `AGENTS.md`의 "명령"에 적은 그 글자 그대로를 `Bash(<명령> *)` 꼴로 넣는다(스크립트로 부르는 프로젝트면 스크립트 호출 명령).
- `ask`에 더한다: 이 프로젝트의 패키지 관리 도구로 패키지를 설치·추가·제거하는 명령.
- 승인받은 플러그인은 `enabledPlugins`에 `"<플러그인>@<마켓플레이스>": true`로 적는다.
- 프로젝트가 쓰지 않는 도구의 명령은 넣지 않는다.

**.claude/rules/** — 머리말의 `paths`를 이 프로젝트의 실제 경로 무늬로 바꾼다. 경로는 프로젝트 뿌리 기준이다. `user-experience.md`는 사람이 마주하는 모든 부분(화면, 명령줄 입출력, 공개 API), `visual-design.md`는 그중 화면을 그리는 파일만 가리킨다. 화면만 있는 앱에서는 두 무늬가 같아도 된다. `visual-design.md`에서 디자인 값을 모아 둔 곳이 아직 없으면 그 줄을 "글꼴, 색, 간격을 모아 둘 곳이 아직 없다. 화면을 더 만들기 전에 한 곳을 정하자고 사용자에게 제안한다"로 바꿔 쓴다. `user-experience.md`의 "이 프로젝트에서는" 절은 결과물 형태에 맞는 줄만 남긴다.

**.claude/hooks/** — `format-after-edit.js`, `check-before-stop.js`는 본 그대로 복사하고, `vibe-kit.json`에 명령을 채운다. 승인받지 않은 쪽은 비워 둔다. 그리고 `.claude/settings.json`에 승인받은 훅만 등록한다:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/format-after-edit.js"], "timeout": 60 }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/check-before-stop.js"], "timeout": 300 }
        ]
      }
    ]
  }
}
```

자동 정리 명령은 프로젝트에 설치된 포맷터를 부르는 꼴로 적고, 없을 때 내려받아 실행하는 꼴은 쓰지 않는다. `extensions`에는 그 포맷터가 다루는 확장자 중 이 프로젝트에 실제로 있는 것만 넣는다.

이 훅은 Node.js로 돈다. `node --version`이 실패하면 훅을 등록하지 않고 그 사실을 보고한다.

**docs/agent/** — `STATE.md`의 "지금까지 한 일"에 오늘 날짜와 setup 실행을 적는다. "다음 할 일"과 "열려 있는 질문"에는 1~2단계에서 실제로 나온 것(미정으로 남은 명령, 설치가 필요한 도구, 사용자가 미룬 결정)만 적고, 없으면 "없음"이라고 쓴다. `STACK.md`의 "쓰는 버전"은 패키지 파일에 적힌 값이나 `--version` 출력을 적고, 알 수 없으면 "미지정"이라고 쓴다. "마지막 점검"은 최신 버전을 하나도 확인하지 않았으면 "없음"이라고 쓴다. `STACK.md`에는 1단계에서 찾은 주요 언어·프레임워크·도구를 한 줄씩 넣고, "마지막 점검"과 확인 날짜는 실제로 공식 출처에서 최신 버전을 확인한 것만 오늘 날짜로 적는다. 확인하지 않은 줄의 "확인한 최신 버전"과 "확인 날짜"는 "미확인"으로 둔다.

**플러그인** — 설치는 승인받은 것만, 프로젝트 범위로 한다: `claude plugin install <플러그인>@<마켓플레이스> --scope project`.

**완료 조건**: 승인받은 파일이 모두 있고, 승인받지 않은 파일은 없다.

## 4단계: 이미 환경이 있을 때 (합치기)

1단계에서 위 파일 중 하나라도 이미 있었으면 그 파일은 다음 순서로 다룬다.

1. 지금 내용과 이 스킬이 만들려는 내용을 비교해, 더할 줄·바꿀 줄·그대로 둘 줄로 나눠 보여 준다.
2. 사용자가 손으로 쓴 내용은 지우지 않는다. 겹치는 줄은 하나로 합치고, 서로 어긋나는 줄은 어느 쪽을 남길지 묻는다.
3. `.claude/settings.json`은 기존 항목을 유지한 채 빠진 규칙만 더한다. 기존 `deny`와 `ask` 규칙은 빼지 않는다.
4. 승인받은 뒤에 고친다.

## 5단계: 확인과 보고

만든 뒤 하나씩 실행해 확인한다.

1. `.claude/settings.json`과 `.claude/hooks/vibe-kit.json`이 올바른 JSON인지: `node -e "JSON.parse(require('fs').readFileSync('<파일>','utf8'))"`가 오류 없이 끝난다.
2. 만든 파일에 `{{` 가 남아 있지 않다.
3. 규칙 파일의 `paths` 무늬마다 실제로 맞는 파일이 하나 이상 있다(새 프로젝트라 아직 없으면 그렇게 적는다).
4. 만든 파일에 이 프로젝트가 쓰지 않는 기술의 이름이나 명령이 없다. `AGENTS.md`, `.claude/settings.json`, `.claude/rules/`, `.claude/hooks/vibe-kit.json`, `docs/agent/STACK.md`에 나오는 도구·언어·명령 이름을 하나씩 뽑아, 1단계에서 파악한 기술 목록에 있는지 본다. 목록에 없는 이름이 있으면 지운다.
5. `AGENTS.md`가 70줄을 넘지 않는다.
6. 훅을 등록했으면 예시 입력으로 직접 실행한다: `echo {} | node .claude/hooks/check-before-stop.js`. 종료 코드가 0이고 **아무것도 출력되지 않아야** 통과다. `"decision":"block"`이 출력되면 검사 명령이 실패한 것이다. 원인이 설치되지 않은 도구면 그 명령을 `vibe-kit.json`에서 빼고 보고에 적는다. 원인이 프로젝트의 기존 실패면 그대로 두고 보고에 적는다.

보고에는 다음을 넣는다: 만든 파일 목록, 만들지 않은 파일과 이유, 실행한 확인 명령과 결과, 확인하지 못한 것, 그리고 "설정과 규칙은 새 세션부터 적용된다"는 안내. 변경은 프로젝트 코드와 분리된 `chore(agent): 키트 환경 추가` 커밋으로 남기자고 제안한다. 프로젝트 폴더 바로 안에 `.git`이 있을 때만 제안한다. 위쪽 폴더가 저장소인 경우에는 제안하지 않고 그 사실을 보고에 적는다.

**완료 조건**: 위 여섯 항목의 결과가 보고에 들어 있고, 통과하지 못한 항목은 고쳤거나 통과하지 못했다고 적혀 있다.
