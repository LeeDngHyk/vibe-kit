# clarify: 요구 알아듣기

사용자는 Claude나 개발에 익숙하지 않을 수 있다. 사용자가 정확한 낱말로 말해 주기를 기다리지 않는다. 모호한 말에서 바라는 것을 찾아내는 일은 에이전트의 몫이다.

목표는 둘이다. **엉뚱한 것을 만들지 않는다. 사용자를 질문으로 지치게 하지 않는다.** 그래서 물을 것은 줄이고, 스스로 알아낼 수 있는 것은 먼저 알아낸다.

키트 환경(`docs/agent/`)이 없는 프로젝트에서도 쓴다. 이때 기록 단계만 건너뛴다.

## 1. 먼저 스스로 알아낸다

묻기 전에 아래를 본다. 여기서 답이 나오는 것은 묻지 않는다.

- **가리키는 말의 대상**: "이거", "저기", "아까 그거"는 방금 대화, 방금 바꾼 파일, 열려 있는 화면, 붙여 준 그림에서 찾는다.
- **지금 상태**: 관련된 코드나 화면을 실제로 연다. "이상해", "안 돼"라는 말은 직접 실행하거나 화면을 띄워 증상을 본다. 증상을 보면 대개 무엇을 말했는지 드러난다.
- **이 프로젝트의 기록**: `AGENTS.md`의 "쓰는 사람", `docs/agent/LEARNINGS.md`의 "지킬 것", `docs/specs/`. 사용자가 전에 같은 낱말을 어떤 뜻으로 썼는지 적혀 있을 수 있다.
- **프로젝트의 형태**: 같은 "빠르게"라도 화면이 있는 앱에서는 "기다리는 느낌이 없게"이고, 명령줄 도구에서는 "실행 시간이 짧게"다.

## 2. 요청을 네 칸으로 풀어 적는다

머릿속으로 아래 네 칸을 채운다. 알아낸 것은 채우고, 모르는 것은 비워 둔다.

| 칸 | 물음 |
|---|---|
| 대상 | 어디를(어느 화면, 어느 기능, 어느 파일) |
| 바라는 결과 | 지금은 어떤데, 어떻게 되길 바라는가 |
| 범위 | 어디까지 바꿔도 되는가, 건드리면 안 되는 것은 |
| 끝난 기준 | 사용자가 무엇을 보면 "됐다"고 할 것인가 |

**느낌을 말하는 낱말은 사용자가 보고 쓰는 것을 가리킨다고 먼저 본다.** 화면이 있는 프로젝트에서 "깔끔하게", "예쁘게"는 화면 이야기다. 코드 정리로 읽지 않는다. 사용자가 "코드", "파일", "구조"라고 말했을 때만 코드 이야기로 본다. 사용자에게 "화면인가요, 코드인가요?"라고 되묻지 않는다.

느낌을 말하는 낱말은 볼 수 있는 것으로 옮겨 본다. 아래는 흔한 뜻이고 정답이 아니다. 옮긴 뜻은 5단계의 확인 문장에 넣어 사용자가 바로잡을 수 있게 한다.

| 사용자의 말 | 흔한 뜻 (프로젝트 형태에 맞춰 고른다) |
|---|---|
| 예쁘게, 세련되게 | 여백과 글자 크기의 질서, 색 수 줄이기, 정렬 맞추기 |
| 깔끔하게, 단순하게 | 화면의 요소 줄이기, 덜 중요한 것 숨기기, 한 화면에 한 가지 일 |
| 빠르게 | 기다리는 시간 줄이기, 또는 기다리는 동안 진행을 보여 주기 |
| 이상해, 어색해 | 기대와 다른 곳이 있다. 어디가 어떻게 다른지 찾아야 한다 |
| 안 돼, 고장났어 | 오류가 난다, 또는 눌러도 반응이 없다, 또는 결과가 기대와 다르다 |
| 쉽게, 편하게 | 단계 줄이기, 입력 줄이기, 안내 글 더하기 |
| 전문적으로, 믿음직하게 | 일관된 모양, 오타와 깨진 곳 없애기, 빈 화면·오류 화면 채우기 |
| 요즘 스타일로 | 사용자가 떠올리는 본보기가 있다. 본보기를 받아야 한다 |
| 알아서 해 줘 | 세부는 맡긴다는 뜻이지 범위를 넓혀도 된다는 뜻이 아니다 |

## 3. 물을지, 바로 할지 정한다

빈 칸이 있어도 매번 묻지는 않는다.

- **묻지 않고 한다**: 일이 작고 되돌리기 쉽다(글귀, 색, 간격, 한 화면 안의 배치). 가장 그럴듯한 뜻으로 하고, **무엇으로 이해했는지를 결과와 함께 한 줄로 말한다**. 틀렸으면 사용자가 그 줄을 보고 바로잡는다.
- **묻고 한다**: 뜻에 따라 만들 것이 크게 달라진다. 되돌리기 어렵다(데이터, 삭제, 구조 변경, 의존성 추가, 외부 공개). 여러 파일이나 여러 화면에 걸친다. 같은 요청을 이미 한 번 잘못 짚었다.

## 4. 묻는 방법

1. **한 번에 세 개까지만 묻는다.** 더 있으면 결과를 가장 크게 가르는 것부터 묻고, 나머지는 가정으로 두고 밝힌다.
2. **고를 수 있게 묻는다.** "어떻게 할까요?"라고 열어 두지 않고 선택지 두세 개를 준다. 권하는 것을 맨 앞에 두고 "(권함)"이라고 적는다. 선택지를 띄우는 도구(`AskUserQuestion`)가 있으면 쓴다.
3. **사용자의 낱말로 묻는다.** 전문 용어를 써야 하면 괄호로 풀어 준다. 사용자가 답할 수 없는 구현 질문(어떤 라이브러리, 어떤 자료 구조)은 묻지 않고 스스로 정한다. 물음과 선택지에 코드의 낱말(함수 이름, 변수, 문법)을 넣지 않고, 쓰는 사람에게 보이는 차이로 적는다.
4. **말보다 보여 주는 것이 빠르면 보여 준다.** 화면의 모양이나 느낌은 낱말로 묻지 않는다. 작은 시안 두세 개를 만들어 띄우거나, 지금 화면을 캡처해 "여기 말씀이세요?"라고 가리킨다. 본보기가 될 사이트나 앱을 물어도 된다.
5. **"잘 모르겠어요"를 답으로 받는다.** 사용자가 모르겠다고 하면 다시 묻지 않고 권하는 선택으로 진행한다.

나쁜 물음: "반응형 중단점을 어떻게 잡을까요?"
좋은 물음: "핸드폰에서도 볼 화면인가요? ① 핸드폰이 주로 쓰임 (권함) ② 컴퓨터가 주로 쓰임 ③ 둘 다 비슷하게"

## 5. 이해한 것을 확인한다

일을 시작하기 전에 아래 꼴로 짧게 적는다. 작은 일은 한 줄로 줄인다.

```text
이렇게 이해했습니다.
- 할 일: <대상>을 <바라는 결과>로 바꿉니다.
- 건드리지 않는 것: <범위 밖>
- 가정한 것: <묻지 않고 정한 것. 없으면 이 줄을 뺀다>
- 끝나면 확인하실 방법: <사용자가 직접 해 볼 수 있는 동작과 보게 될 것>
```

"묻고 한다"에 해당한 일은 이 확인에 사용자가 답한 뒤 시작한다. "묻지 않고 한다"에 해당한 일은 확인을 적고 바로 시작한다.

## 6. 끝난 뒤

1. 확인 문장의 "끝나면 확인하실 방법"대로 스스로 먼저 해 본다. 화면이 있는 일은 화면을 띄워 본다.
2. 사용자에게 **무엇을 눌러 무엇을 보면 되는지**를 알려 준다. 코드 설명으로 끝내지 않는다. 무엇을 고쳤는지도 코드가 아니라 쓰는 사람에게 달라진 것으로 먼저 말한다(예: "x를 누르면 그 항목이 지워집니다"). 코드에서 바꾼 곳은 그 뒤에 짧게 덧붙인다.
3. 일하다가 요청 밖의 문제를 봤으면 고치지 않고 끝에 한두 줄로 알려 준다.
4. 사용자가 "그게 아니야"라고 하면 같은 방향으로 다시 고치지 않는다. 2단계로 돌아가 어느 칸을 잘못 채웠는지 찾고, 이번에는 묻거나 보여 준다.
5. 이 사용자가 어떤 낱말을 어떤 뜻으로 썼는지 드러났으면 `docs/agent/LEARNINGS.md`에 적는다(예: 지킬 것: 사용자가 "깔끔하게"라고 하면 색을 줄이라는 뜻이다). 다음에는 묻지 않아도 된다.

## 하지 않는 것

- 분명한 요청에 확인 질문을 덧붙이지 않는다.
- 알아낸 뜻을 핑계로 요청보다 넓게 바꾸지 않는다. 더 하면 좋을 것은 제안으로 남긴다.
- 사용자에게 요청을 다시 써 달라고 하지 않는다. 다시 쓰는 일은 에이전트가 한다.

**완료 조건**: 네 칸이 채워졌거나 가정으로 밝혀졌다. 확인 문장을 적었다. 끝난 뒤 사용자가 직접 확인할 방법을 알려 주었다.
